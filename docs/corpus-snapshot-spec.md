# Corpus snapshot — spec (draft for Advisor gate)

Date: 2026-10-17. Status: GATED (Security Advisor PASS_WITH_CHANGES,
all required edits folded: completion marker + finalize PATCH,
readonly report open, fingerprint carries vector counts, ISBN
re-cleaned at build, work_id UUID-shape projection) and the
migration is APPLIED + verified 2026-10-17. The writer build is in
flight against this spec.

## 1. Problem

Run history (v2.13.6) mirrors what a run did. It says nothing about
the corpus that already exists on the machine: which works are in
`corpus.db`, whether their text/vectors are complete, which parser
generation stamped them, or whether a work's stored text changed
since the last time anyone looked. Verifying the corpus today means
reading a `--corpus-status` printout on the machine and trusting the
paste.

## 2. Proposal

A standalone, explicit command —

```
py .\process-portable.py --corpus-snapshot
```

— reads the local corpus in report mode, builds a metadata-only
snapshot (one header row + one row per corpus work), and uploads it
to two new tables in the existing `processor` schema. A snapshot is
a point-in-time observation of the corpus, not a run and not a sync:
nothing flows back, the local corpus is never modified, and ordinary
runs (including `--run-history` runs) never take one implicitly in
v1. Re-running the command records a new snapshot; the pair
(header, works) is the unit of history, so "what changed since last
time" is a diff between two snapshots.

## 3. Acceptance questions

1. What works are in the corpus on a machine right now, in what
   completeness state, at what vector coverage?
2. Which works are stale-parser, partial, ingesting, or failed?
3. Did a work's text or source file change between two snapshots
   (fingerprint + text_root_hash + source_hash comparison)?
4. What is the corpus's size, embedding generation, and last-recorded
   canary state over time?
5. Quote inventory per work and in total, by status — counts only.
6. Joins: snapshot works ↔ `works` (work_id), ↔ run-history books
   (book_key / fingerprint), ↔ the local corpus (fingerprint).

## 4. Tables

### processor_corpus_snapshots — one row per snapshot

| Column | Type | Notes |
|---|---|---|
| id | uuid PK, default gen_random_uuid() | |
| snapshot_key | text UNIQUE NOT NULL | `snapshot-<uuid4 hex>` generated by the writer; a snapshot is an observation, so a retry is a new row, never an overwrite |
| captured_at | timestamptz NOT NULL | when the local read happened (UTC) |
| machine_label | text NULL | the user's chosen `machine_label` config; never auto-collected |
| processor_version | text | PORTABLE_VERSION of the snapshot writer |
| corpus_parser_version | text | CORPUS_PARSER_VERSION in force |
| corpus_v | text NULL | corpus schema generation (`CORPUS_V`) |
| corpus_fingerprint | text NOT NULL | sha256 over the canonical sorted per-work identity set (§6) — the content identity of the whole corpus; equal fingerprints = no measured change |
| works_count | int NOT NULL | number of work rows in this snapshot |
| corpus_bytes | bigint NULL | corpus.db size as the status read model measures it; NULL if unmeasured |
| size_breakdown | jsonb NOT NULL default {} | {text, fts, vectors, other, total, via} — numbers only |
| fts_available | boolean NULL | whether FTS5 answered on this machine's SQLite |
| current_generation | jsonb NULL | explicit projection of the current embedding generation: {model, format, dim, canary, born, checked} — names/state only (§5) |
| generations | jsonb NOT NULL default [] | the same projection for every recorded generation |
| totals | jsonb NOT NULL default {} | {works, by_status, quotes, quotes_by_status} — measured counts |
| complete | boolean NOT NULL default false | completion marker: set true by a finalize PATCH only after every book chunk has landed with its expected count. A snapshot with complete = false is a partial upload and is never a verification source (§10 reads complete snapshots only) |
| uploaded_at | timestamptz NOT NULL default now() | |

## 5. Transfer list

**Transferred:** exactly the §4 fields — timestamps, versions,
counts, hashes, book metadata (title/author/ISBN/series), corpus
state, embedding model names and generation state, size numbers.

**Never transferred:**

- Book text, chapter text, passages, FTS content — in any field.
- Passage vectors / embeddings of any kind. This includes the
  generation meta's **canary sentinel vectors and cosines**: the
  writer projects generation records down to
  {model, format, dim, canary, born, checked} and the test suite
  seeds sentinel-laden meta and asserts none of it ships.
- Quote text, evidence strings, stage payloads or stage outputs.
- Filenames and paths: `corpus_works.payload.source_name`, the learn
  directory, and the corpus.db path never ship. (The status read
  model carries the directory for local display; the snapshot
  builder must not inherit it.)
- Raw identifier lists and ASIN (ISBN-13 only — and the stored ISBN
  is re-cleaned through `_clean_isbn` at build time, so "cleaned
  ISBN-13 only" is provable against legacy or hand-edited rows, not
  just trusted from ingest).
- The raw corpus payload / envelope JSON (fields are projected
  individually, never copied wholesale).
- API keys, endpoint/base URLs, hostnames — as in run history.

Unknown stays NULL, never 0 (the run-history doctrine): vectors and
coverage under no current generation, words when the payload has
none, hashes the local row does not carry.

## 6. Snapshot identity

`corpus_fingerprint` = sha256 of the canonical JSON of:

- the current generation's {model, format} (or null), and
- the per-work tuples (fingerprint, status, parser_version,
  text_root_hash, source_hash, current-generation vector count),
  sorted by fingerprint.

Machine label and capture time are NOT inputs: the same corpus on
another machine produces the same fingerprint. corpus.db byte size
is reported but is not identity (WAL/free-page layout varies).
Equal fingerprints mean no change **in the fingerprinted set** —
text, source, status, parser generation, and vector counts. Quote
counts are deliberately NOT fingerprinted: curation churn (verify /
select / retract) should not re-identify the corpus; quote changes
remain visible by diffing the book rows themselves.

## 7. Command semantics

- `--corpus-snapshot` is a standalone dispatch like `--corpus-status`:
  it loads config, acts, exits. It does NOT require `run_history`
  config or `--run-history` — invoking it is itself the named act.
- The read is local-write-free and uses the readonly report open
  directly — `CorpusDB.open(learn_dir, mode="report", readonly=True)`
  — NOT the shared `_corpus_db_for` helper: a non-readonly handle's
  open path writes probe stamps into meta and can create the FTS
  index, which would make the snapshot mutate the corpus it
  observes. The builder takes no canary check (no embedder call, no
  network), so a generation's `canary` value is the state as last
  recorded by corpus operations, and the spec says so wherever the
  value is described. A snapshot never mutates corpus.db (pinned by
  a dump-hash test).
- Corpus absent (no corpus.db) → print that there is nothing to
  snapshot, exit 2, upload nothing. Corpus corrupt/unavailable (the
  open discipline preserves it as `.corrupt` and prints its own
  warning) → report unavailable, exit 2 — never print "nothing to
  snapshot" over a corruption event. Corpus present with zero works
  → a valid snapshot with works_count 0.
- Supabase not configured → error, exit 2, upload nothing.
- Upload order: header insert (complete = false) → book rows in
  chunks of 200, each chunk required to return exactly its row
  count → finalize PATCH setting complete = true. If any chunk
  fails or returns an unexpected count, the writer DELETEs the
  header (children cascade), prints the failure and the snapshot
  key, and exits 1 — a failed snapshot leaves no partial snapshot
  behind. If the header POST itself returns no response (a landed
  row the writer never saw), the writer probes by snapshot_key —
  client-generated and UNIQUE — and deletes a landed header before
  exiting 1; if the probe cannot confirm, the message names the
  snapshot key for manual cleanup. A delete is confirmed only by a
  non-None, non-empty response; anything else names the key.
- Success prints the snapshot key, works count, corpus fingerprint
  (short form), and size. With `--json`, a compact receipt
  {snapshot_key, captured_at, works, corpus_fingerprint} prints
  instead — never the full payload.
- Malformed local JSON (identifiers / payload / generation meta) is
  projected as absent fields, never a crash and never shipped raw.

## 8. Security posture (inherited from run history, RH-4)

Same `processor` schema, same rules: RLS enabled with zero policies,
grants to service_role only, no grants to anon/authenticated, the
writer rides the existing REST helper's schema targeting. Migration
custody = processor repo, never numbered into the app sequence.
work_id is a soft reference with no FK in either direction.

Retention: snapshots are kept (the run-history RH-1 posture) — the
migration header names the exit (delete by captured_at, or drop
both tables) as available only on a future explicit ruling.

## 9. Tests (writer's suite, fake transport at the sb() seam)

1. Payload builder over a seeded corpus (complete + partial works):
   every §4 book field asserted, incl. words from payload, per-work
   quote counts, current-generation vector count/coverage, and
   NULL vectors/coverage when no generation exists.
2. Generation projection: seeded meta carrying sentinel vectors /
   cosines ships only the six projected keys.
3. Denylist scan over all built payloads with a hostile corpus
   (source_name set, path-like payload values): no source_name, dir,
   path, raw identifiers, ASIN, sentinel, vector, text, or payload
   keys/values anywhere.
4. corpus_fingerprint: deterministic across capture times; changes
   when a work's source_hash changes; identical for identical state.
5. Transport: header → chunked books → finalize PATCH order + schema
   targeting; complete is set only on full success; a failed chunk
   triggers the header DELETE and a failure result; a header POST
   returning None triggers the snapshot_key probe (landed → delete,
   unconfirmed → the key is named); missing Supabase config makes
   zero calls.
6. Absent corpus → no calls, exit-2 result. Empty corpus → header
   with works_count 0 and no book calls.
7. CLI: parser accepts --corpus-snapshot; main() dispatch routes to
   the command (and does not arm run history).
8. Local immutability: corpus dump hash identical before/after the
   payload build.

Full suite at/above the 1615 baseline, never regressed.

## 10. First-live verification

After the migration applies (four-part check as in run history:
catalog grants, RLS + zero policies from the catalog, anon probe,
authenticated probe, service-key round trip on the new tables):

1. The user pulls, runs `--corpus-snapshot`.
2. Luna reads the latest **complete = true** snapshot back over SQL
   and reconciles:
   works count, per-status counts, per-work chapters/passages/
   coverage, totals, and corpus fingerprint — against the user's
   `--corpus-status` output for the same corpus state.
3. Any mismatch is a finding against the writer, fixed before the
   snapshot is treated as a verification source.

## 11. Non-goals (v1)

- No automatic snapshots on ordinary runs or watch cycles.
- No stage-output / retrieval detail (the envelope/stage summary is
  a named v2 candidate if questions need it).
- No pruning, diffing UI, or app-side consumption.
- No changes to run history.
